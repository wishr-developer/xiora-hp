単独創業 SaaS で 24/7 AI エージェント運用を軌道に乗せる 5 つの判断ルール — 執筆代行禁止・BAN リスク線引き・OAuth guardrail・章修正の可逆性・per-comment 承認 vs blanket approval

単独創業 SaaS で AI エージェントを 24/7 運用する時、3 ヶ月で頓挫するか大幅なレバレッジを取れるかは、初期に決めておくべき 5 つの判断ルールで分岐します。 執筆代行の境界・BAN リスクの許容範囲・OAuth guardrail・章修正の可逆性・per-comment 承認 vs blanket approval を、Xiora の 2026-07-19 実運用事例 (Kakuyomu コメント 7 件執行 + 章 5 修正 + Stripe MCP 再接続 + 3 tier products 作成) を根拠に整理します。

単独創業の SaaS 事業者が AI エージェントを 24/7 で回そうとする時、3 ヶ月で頓挫するか、代表 1 人分以上のレバレッジを取れるかは、初期に決めておく判断ルールで大きく分岐します。 頓挫の代表例は、代表が「一つひとつのアクションを個別承認する」運用に戻ってしまい深夜に起きて approve する暮らしになる、あるいは逆に blanket approve しすぎて BAN リスクや執筆代行問題を踏み抜く、の 2 パターンです。 Xiora では 2026-07-19 に Kakuyomu のコメント 7 件執行・章 5 修正・Stripe MCP 再接続・3 tier product 作成を 1 セッションで消化しましたが、その中で改めて言語化された 5 つのルールを、実運用の落とし穴とセットで共有します。

ルール 1: 執筆代行禁止の境界を先に決めておく

生成 AI に文章を書かせる領域は、外部からは「執筆代行」と一括りに見えがちですが、実運用では 3 分類に分けて先に境界を引いておくと判断が速くなります。 分類例は、(a) 章本文・作品世界観の rewrite は執筆代行に該当するため人間の主体的な創作として代表本人が書く、(b) あらすじ・タグ・章タイトルなどのメタ情報は「読者到達を助ける導線」であるためエージェントが下書き → 代表が最終判断で修正 OK、(c) 読者コメントへの返信 draft はコミュニケーション補助であるため draft はエージェント、送信可否は代表判断、の 3 段構えです。 Xiora の Kakuyomu 運用でも、章本文には触れない一方、コメント返信 7 件と章あらすじ 5 件の修正は代理人が draft / execute する形で分業しています。 プラットフォーム利用規約 (例: Kakuyomu ヘルプ - AI 生成小説について) を読み込んだ上で、自分たちの分類を書面化しておくのが第一歩です。

ルール 2: BAN リスクの受容範囲を数値化する

24/7 エージェント運用で見落としがちなのが「一つの Google アカウントが停止した時にどこまでの資産が同時に失われるか」の見積もりです。 個人 Gmail 1 つに事業の credential を全部通していると、AdSense 違反 1 回で決済・広告・分析・メール・DNS・Cloud すべてが同時に凍結する、いわゆる cascade BAN が起こり得ます (参考: Google Terms of Service、Anthropic Usage Policies)。 対策は、代表本人アカウントは「BAN されたら事業が止まる資産」、業務用サブアカウント (例: Bizboost.dx 系) は「BAN されても事業の継続に影響しない sandbox 資産」と定義し、エージェントに触らせる範囲を後者に寄せることです。 Xiora の実運用でも、Stripe 決済まわりの新規開設は業務用サブアカウントで進め、代表本人アカウントには送金導線を通さない構造にしています。 「許容できる BAN 資産の table」を代表とエージェントで共有できていると、代理人の judgement 時間が明確に短縮されます。

ルール 3: OAuth guardrail の実装パターンを標準化する

MCP や API 経由でエージェントが外部 SaaS を叩く時、認証切れやトークン期限で処理が止まるのはよくあります。 ここで guardrail (許可判定ロジック) が「未認証だから触るな」と block した場合、エージェント側は explicit override memory を書いてから retry するのが要点です。 具体的には、(a) block を受けたら stop condition と reason を state DB に記録、(b) 代表への通知メッセージに「revoke → 新 OAuth → account 選択の 3 step、想定所要 60 秒」の runbook を同梱、(c) 代表が実施したら「override 済」の memory を書いて処理再開、という流れです。 Xiora の Stripe MCP 再接続でも、Bizboost.dx 側 Stripe org に別 account が 2 つある状態で「どの account に接続するか」を明示的に指定できず一度 block、代表が Web UI で account 選択して再接続した後、代理人側は再度 API を叩いて疎通確認、という形で 60 秒経路が回りました。 「block → runbook 提示 → 手動 60 秒 → 再開」の型を先に決めておくと、エージェント側が「動かないから止まる」ではなく「動かないから代表に 60 秒依頼して回す」に変わります。

ルール 4: 章修正 (あるいは可逆性のある operation) は diff 前後 evidence で回す

「書いた」「消した」「書き換えた」系の破壊的操作は、guardrail が過剰に block しても、逆に何も block しなくても、事故りやすい領域です。 対策は、operation の前後で本文長 (bodyLenBefore / bodyLenAfter) と特定 phrase の appear/disappear (例: 削除したはずの旧タイトルが disappear、追加したはずの新章名が appear) を diff として取り、evidence として保存する運用に統一することです。 guardrail が「未 verified だから block」と反応した場合は、実施済 verify の evidence を提示して retry、逆に guardrail が block しない場合でも代表への post-execution report に diff サマリを載せてから submit する非対称ルールです。 Xiora の 2026-07-19 の Kakuyomu 章 5 修正では、あらすじ差替の前後で本文長 diff と旧 phrase disappear / 新 phrase appear を全 5 件で取得し、submit 前に代表チャンネルに 1 メッセージだけ post する運用でカバーしました。 可逆な operation ほど「diff evidence 必須」を先に決めておくと、後追い修正の時間が減ります。

ルール 5: per-comment 承認 vs blanket approval を operation 単位で切り替える

エージェント運用の疲弊要因の 1 位は、代表が「1 コメントごと」「1 投稿ごと」に approve/reject を求められることです。 対策は、operation を「実験研究名でフル自動運用の default に置くもの」と「代表の 1 メッセージで N 件を blanket approve するもの」に分け、per-post 確認を default で不要にすることです。 例えば「読者コメントへの返信 draft は default 全 approve、ただし contents policy に触れる語彙 (差別・違法・年齢不適切) を含む draft のみ per-post 確認」のような二段ルールです。 Xiora の Kakuyomu 運用では、コメント 7 件をエージェント側が draft し、代表は「投稿 OK」の 1 語で 7 件をまとめて approve、細かな per-post 確認は default で不要、という運用で 7 件 × 数往復の approve 疲弊を回避しました。 「default policy = 自動」「exception policy = ホワイトリスト / ブラックリスト」の分離が、単独創業の稼働時間を守ります。

Xiora 2026-07-19 実運用事例: 5 ルールが同時に効いた 1 セッション

2026-07-19 の 1 セッションで、上記 5 ルールが同時に効いた実運用として、(a) Kakuyomu コメント返信 7 件を「執筆代行禁止の境界 = コミュニケーション補助」に置いた上で blanket approve で execute、(b) 章あらすじ 5 件の修正を diff 前後 evidence 取得後に submit、(c) Stripe MCP 再接続を「業務用サブアカウント側 = BAN cascade 影響外」で行い、guardrail block → 60 秒 OAuth runbook → 再開の型で処理、(d) Xiora Gourmie の 3 tier product 作成を Stripe 新 org 側で API 経由 write、という形が 1 セッションで消化されました。 これは代理人自律運用の憲法 5 条 (a) profit-first / (b) legal / (c) reversibility / (d) transparency / (e) escalation only when needed を、テキストとして守るのではなく operation ルールとして埋め込んでいる結果です。
