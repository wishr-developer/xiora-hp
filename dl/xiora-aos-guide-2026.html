0. はじめに

1. Xiora Autonomous Company OS とは

1.1 定義

Xiora Autonomous Company OS (以下、ACOS) とは、創業者が寝ている間も事業が回るための、AI エージェント群 + 常駐ハンドラ + 人間ゲートの 3 要素で構成される、24/7 稼働型の実装 pattern です。

ここで重要なのは「OS」という命名です。 ACOS は特定のプロダクトではなく、複数のプロダクト (Xiora の場合、Kigen / Aiverse / Nexa Academy / Gourmie / Ocean など 20+) を横断的に運用するための、基盤となる実装レイヤです。 macOS が Safari や Photos の下で動く OS であるのと同じ位置づけです。

1.2 なぜ「OS」なのか

従来の SaaS 起業では、プロダクトごとに個別の運用チームや自動化スクリプトを書いていました。 例えば Kigen のリマインダー配信、Aiverse のライブ配信管理、Nexa の受講生対応、Gourmie の口コミ返信、これらは別々のコードベースで管理されていました。

しかし、1 人で 20+ プロダクトを回すには、この方式では破綻します。 プロダクト A で顧客対応が滞っている間、プロダクト B の障害が発生する、という事態が日常的になるからです。

ACOS はこれを、以下の共通レイヤで統一します:

  1. ブレイン (Brain) — 全プロダクトを横断する意思決定エンジン (Ollama + SQLite state.db)
  2. ハンドラキュー (Handler Queue) — 全プロダクトのタスクを 1 本のキューで処理
  3. AI 社員 (AI Employees) — 各役割を担う専門エージェント (代表秘書、コード書き、SRE、リサーチャなど)
  4. 人間ゲート (Human Gates) — 創業者が最終決裁する 5 種類のイベントのみを浮上させる

1.3 ACOS の 3 原則

原則 1: 人間ゲートは 5 種類のみ

全ての意思決定を人間に浮上させると、創業者は寝る時間がなくなります。 ACOS は、以下 5 種類のイベントのみを人間ゲートとして定義し、それ以外は AI が最終決裁します:

  • billing: 外部送金 (Stripe payout / 銀行送金 / 経費精算)
  • delete: データ削除 (customer 削除、DB drop、file rm -rf)
  • permission: 権限昇格 (root 権限、admin 権限、API scope 拡大)
  • contract: 契約締結 (NDA、業務委託、雇用契約)
  • kyc: 本人確認 (marketplace 登録、金融口座開設)

これ以外の全てのタスク (X 投稿、Gmail 返信、コードのコミット、handler 実装、broadcast など) は AI が最終決裁します。 「AI に判断させて大丈夫か」と迷ったら、この 5 種類に該当するかで判定します。

原則 2: 状態は SQLite の 1 ファイルに集約

複雑な分散システムを回避し、全プロダクト横断の状態を state.db という 1 個の SQLite ファイルに集約します。 18 テーブル (agent_skill, handler_queue, halt, kv_store, event, ... ) で全 20+ プロダクトの状態を管理します。 バックアップも cp state.db backup/ の 1 行で完結します。

原則 3: 常時課金ゼロで開始

MRR ¥50,000 に達するまでは、追加の月額課金を一切増やしません。 Ollama (ローカル)、SQLite (ファイル)、launchd (macOS 内蔵)、Vercel Free、Cloudflare Free、Neon Free、Railway trial の組み合わせで、原価ゼロで運用します。 MRR ¥50,000 を超えたら、収益の 20% までを SaaS ツール課金の上限とします。

1.4 なぜ 1 人で 20+ プロダクトを回せるのか

答えは 3 つあります。

第一に、ハンドラという抽象です。 全てのタスクを「input → handler → output」という 1 パターンに落とし込むと、Kigen も Aiverse も Nexa も、同じキューで処理できるようになります。 プロダクトが 20 になっても、キューは 1 本のままです。

第二に、AI 社員という役割固定です。 「代表秘書 (Rei)」「コード書き」「SRE」「リサーチャ」といった役割ごとに担当エージェントを固定すると、プロダクトが増えても役割は増えません。 Kigen のバグ調査も Aiverse のバグ調査も、同じ「SRE エージェント」が担当します。

第三に、人間ゲートの 5 種類限定です。 5 種類以外は AI に最終決裁を委譲することで、創業者の時間を「本当に人間しかできないこと」だけに集中させます。

2. 絶対人間ゲート 5 種の具体判定基準

前章で提示した 5 種類の人間ゲートを、実装レベルの判定基準に落とし込みます。 実際の handler は、以下の条件式で「人間ゲートを起こすか / AI が処理するか」を判定します。

2.1 billing ゲート

判定条件:

  • 外部への送金金額が ¥1 以上発生する場合 (Stripe payout、銀行振込、PayPal、経費精算)
  • 定期課金の新規契約 (SaaS 追加、月額サブスク)
  • 課金の解約 (定期収入の停止)

AI が処理する範囲:

  • Stripe webhook 受信 → 内部 DB 更新 (送金は Stripe 経由なので人間ゲート不要)
  • 顧客への請求書自動送信 (金額は AI 決定、ただし送金は Stripe 経由)
  • 経費入力の draft 作成 (最終「支払う」ボタンは人間)

Xiora の実運用例:

  • 2026-07 の Vercel 課金 ¥1,980 → 人間ゲート発火 → Reo 承認
  • Kigen 顧客への月額 ¥600 請求 → 人間ゲート不要 (Stripe 自動)
  • Rakuten アフィリエイト送金受取 ¥3,200 → 人間ゲート不要 (incoming money は自動処理)

2.2 delete ゲート

判定条件:

  • customer データの削除 (GDPR / 個人情報保護法 対応でも人間ゲート)
  • DB スキーマの drop (テーブル削除、カラム削除)
  • ファイルシステムの rm -rf (10 ファイル以上、または 100MB 以上)
  • git branch --delete (main / master / production は禁止、feature branch のみ AI 判断可)

AI が処理する範囲:

  • 一時ファイルの削除 (/tmp 配下、build cache)
  • 個別 email の archive (削除ではなく移動)
  • 期限切れの session 削除 (redis TTL 依存)

Xiora の実運用例:

  • ROOM プロジェクトの Docker volume wipe → 人間ゲート発火 → Reo 承認 (完了済)
  • Test 環境の SQLite drop → 人間ゲート不要 (test は AI 判断可)
  • Production の users テーブル drop → 禁止 (AI がこれを提案しても実行しない)

2.3 permission ゲート

判定条件:

  • root / sudo 権限の獲得 (Vault からの root credential 取得)
  • API scope の拡大 (Gmail send-only → send-and-modify、GitHub read → write)
  • OAuth 認可の新規付与 (新 SaaS への Google/GitHub ログイン)
  • SSH key の追加 (新 VPS への公開鍵配置)

AI が処理する範囲:

  • 既存の read-only API 呼び出し
  • Vault からの read-only credential 取得 (書き込みは人間ゲート)
  • 既に付与済みの scope 内での API 操作

2.4 contract ゲート

判定条件:

  • 業務委託契約の締結 (相手が個人・法人問わず)
  • 雇用契約 (フルタイム、パート、インターン全て)
  • NDA (秘密保持契約)
  • Marketplace の販売者契約 (Amazon KDP、Kindle Direct 等)
  • 継続的な広告出稿契約 (Google Ads、Meta Ads の月額 prepaid 除く)

AI が処理する範囲:

  • 単発の Google Ads / Meta Ads の当月出稿 (月次上限を Reo が事前設定した範囲内)
  • 見積書の自動生成 (送信は人間ゲート)

2.5 kyc ゲート

判定条件:

  • 個人情報 (免許証、マイナンバー、住所) を外部サービスへ提出
  • Marketplace の販売者登録 (Amazon KDP、Kindle、note、Rakuten 等)
  • 金融口座の開設 (法人口座、Stripe account、PayPal Business 等)
  • Web UI からのログイン (パスワード / 2FA 入力を伴うもの)

AI が処理する範囲:

  • 公開情報のみを使ったフォーム記入 (会社名、電話番号、公開メール)
  • 既存 credential での API ログイン (パスワード再入力を要さない)

def is_human_gate(event) -> bool:

3. 憲法 grep とブランド分離

3.1 「憲法」の位置づけ

ACOS では、創業者が譲れないルールを「憲法」と呼びます。 これは単なる ドキュメント ではなく、コード生成時に grep で検査する自動的な gate です。 憲法違反のコード / 記事 / 投稿 は 実装前に reject されます。

Xiora の憲法は以下の 7 項目です:

  1. 外部ブランド (別 プラットフォーム の 別 ペルソナ) は Xiora ブランドの記事に一切出さない
  2. 対面営業は Reo 明示依頼のみ (default 拒否)
  3. 収益化前は月額課金ゼロ、subdomain 活用
  4. UI は白基調ミニマル (Vercel / Linear tone)
  5. Xiora ブランド以外の名義 (Reo 個人名義) は default 禁止
  6. 全事業活動は Xiora 名義 (note / YouTube / marketplace / 請求書)
  7. 全記事は 日本語 native、英訳 は 二次

3.2 憲法 grep の実装

# scripts/const_grep.sh
#!/bin/bash
FILE=$1

# ルール 1: 外部 ブランド (別 プラットフォーム の 別 ペルソナ) が Xiora HP に混入していないか
if grep -i "external_persona_placeholder" "$FILE"; then
  echo "VIOLATION: rule 1 (external persona leaked to Xiora HP)"; exit 1
fi

# ルール 5: Reo 個人名義が Xiora ブランドに混入していないか
if grep -E "個人ブログ|個人サイト" "$FILE"; then
  echo "VIOLATION: rule 5 (individual brand mixed)"; exit 1
fi

# ルール 7: 英語のみ の 記事 になっていないか (日本語コード検出)
if ! grep -P "[\x{3040}-\x{309F}\x{30A0}-\x{30FF}\x{4E00}-\x{9FAF}]" "$FILE" > /dev/null; then
  echo "VIOLATION: rule 7 (no Japanese content)"; exit 1
fi

echo "PASS: constitution grep clean"

このスクリプトを、全 handler の commit 前 hook に組み込みます。 憲法違反があれば、AI がどれだけ「良い」記事を書いても reject されます。

3.3 ブランド分離の実装

Xiora には複数のブランドが並存します:

  • Xiora (主力、企業 SaaS ブランド)
  • Xiora Apps (子ブランド、iOS アプリ Kigen 等)
  • 外部 独立 ペルソナ (完全独立、Xiora と接触禁止 の 別 プラットフォーム 活動)

これらは、以下の方法で 実装レベルで分離します:

  1. リポジトリ 分離: Xiora_HP/ と 外部 ペルソナ の 作業 dir は 別 git repo
  2. 手動 handler 分離: 外部 ペルソナ 用 handler と Xiora HP handler は 別プロセス、共有 state を持たない
  3. 憲法 grep で 相互混入を検出

4. ハンドラキュー 8 ステージサイクル

4.1 ハンドラとは

ハンドラは、ACOS における「1 タスクを処理する 最小単位」です。 全てのタスク (X 投稿、Gmail 返信、code commit、Kigen 顧客対応、Aiverse ライブ配信管理 等) は、共通の handler インタフェースで実装されます。

class Handler:
    name: str
    priority: int  # 1 (低) - 10 (高)

    def can_handle(self, event) -> bool:
        """このハンドラが処理できる event か判定"""

    def process(self, event) -> Result:
        """実際の処理"""

4.2 8 ステージサイクル

ブレインループは、以下 8 ステージを 30 秒サイクルで繰り返します:

  1. ingest: 外部 event (email、webhook、cron trigger、Reo からのメッセージ) をキューに投入
  2. filter: 憲法 grep で禁止 event を除外
  3. dedupe: 同一 event の重複を排除
  4. route: どの handler が処理するか決定
  5. plan: handler が処理計画を立案 (LLM で thinking)
  6. execute: 実処理 (API 呼び出し、DB 更新、ファイル生成)
  7. verify: 実行結果の検証 (成功判定、副作用チェック)
  8. learn: 結果を state.db の event テーブルに記録 (次回の意思決定材料)

4.3 各ステージの実装のコツ

ingest ステージ: 外部 event を「安全に受信する」ことに集中します。 event source ごとに認証を確立 (Gmail は OAuth、Stripe は webhook secret、GitHub は HMAC) し、認証失敗は即 log + drop します。

filter ステージ: 憲法 grep をここで実行します。 「AI に処理を委ねる前に、憲法違反を弾く」のが filter の役割です。

dedupe ステージ: 同一 event の重複処理を防ぎます。 event の hash を state.db.event_hash テーブルで管理し、既存 hash なら skip します。

route ステージ: どの handler が処理するか、rule ベース (優先) + LLM ベース (fallback) で決定します。 rule ベースが 90%、LLM fallback が 10% になるように設計します。

plan ステージ: handler が処理計画を LLM (Ollama) で thinking します。 このステージで人間ゲート判定を実行し、5 種類に該当したら 人間へ通知して pause します。

execute ステージ: 実処理を実行します。 副作用 (外部 API 呼び出し、DB 更新) はここで発生します。 execute の失敗は 3 回まで retry し、それでも失敗なら halt テーブルに記録して人間に通知します。

verify ステージ: execute の結果が期待通りかを検証します。 例: 「Gmail 送信 handler が execute した後、Gmail sent フォルダに件名 X のメールが存在するか」を確認します。

learn ステージ: 結果を state.db.event テーブルに記録します。 これが次回の route ステージで参照され、学習効果が生まれます。 例: 「過去 3 回、handler A は event type X に対して 成功していない」なら、route ステージが handler B に振り替えます。

4.4 30 秒サイクルの根拠

30 秒という間隔は、以下 3 制約のバランスから来ています:

  • Ollama のレイテンシ: LLM thinking は 3-8 秒。 8 ステージ全体で 20 秒程度が limit
  • API rate limit: Gmail / X / Stripe は 30 秒あたり数十 request まで
  • Mac の CPU 負荷: 30 秒 サイクルなら M1 MacBook で 15% CPU 使用率で安定

これより短いサイクル (10 秒) にすると、Ollama が間に合わない handler が発生します。 長すぎるサイクル (5 分) にすると、リアルタイム性が失われます。

5.1 組織構造

6. Zero-spend policy と cost governor

6.1 Zero-spend policy の定義

MRR ¥50,000 に達するまでは、追加の月額課金を一切増やさない、というルールです。 既に契約中の月額課金 (Vercel Pro、GitHub Copilot、Notion 等) は継続しますが、新規の課金は禁止します。

6.2 なぜ zero-spend が重要か

多くの 1 人 SaaS が挫折する原因は、「収益化前にツール課金で 月 ¥30,000 かかり、精神的に追い詰められる」ことです。 Ollama がローカルで動く 2026 年においては、無料層のみで MRR ¥50,000 まで到達可能です。 早期の 課金は 単に 焦りを増やすだけです。

6.3 無料層のみで組む具体構成

  • LLM: Ollama (ローカル、macOS 上で動作)、llama3.2:3b / mistral-nemo 14b
  • DB: SQLite (state.db)、Neon Free (Postgres、0.5GB)、Cloudflare D1 Free
  • Hosting: Vercel Free (100GB bandwidth/月)、Cloudflare Pages Free
  • Storage: Cloudflare R2 (10GB Free)、GitHub Pages
  • Email: Gmail 個人 (無制限)、SendGrid Free (100 通/日)、Resend Free (100 通/日)
  • Domain: xiora-official.com (¥1,500/年、既に契約済)
  • Monitoring: Uptime Robot Free、Better Stack Free
  • Analytics: GA4 Free、Plausible Free
  • CI/CD: GitHub Actions Free (2000 分/月)

これで、MRR ¥50,000 に到達するまで 月額 ¥0 (ドメイン更新の年 ¥1,500 を除く) で運用可能です。

6.4 cost governor の実装

「うっかり 有料 プラン に upgrade する」を 防ぐため、cost governor という handler を実装します:

class CostGovernorHandler:
    def can_handle(self, event):
        return event.type == "billing_change_proposed"

    def process(self, event):
        if event.new_monthly_cost_yen > 0:
            create_human_gate(
                type="billing",
                message=f"{event.service} を ¥{event.new_monthly_cost_yen}/月 に upgrade しようとしています。 MRR ¥50,000 を超えたか確認してください。",
                priority=10
            )

これで、AI agent が「Vercel を Pro プラン に upgrade しよう」と提案しても、人間ゲートで Reo が最終決裁します。

6.5 MRR ¥50,000 到達後のルール

MRR ¥50,000 を超えたら、以下のルールで課金を許可します:

  • 課金上限: MRR の 20% (MRR ¥50,000 なら 月 ¥10,000 まで)
  • 優先順位: セキュリティ > 開発生産性 > 分析 > その他
  • 決裁: 人間ゲート (Reo が最終)、AI は提案のみ

7. 24/7 monitoring と Rei 秘書

7.1 monitoring の 3 層

  • Layer 1 (プロセス): launchd (macOS) / systemd (VPS) でプロセス生存監視
  • Layer 2 (ヘルスチェック): 各プロダクトの /healthz エンドポイントを 1 分間隔で HTTP GET
  • Layer 3 (ビジネス): MRR、DAU、Stripe 失敗率、error rate、を 15 分間隔で集計

7.2 alert の 3 段階

  • P3 (info): log 記録のみ、Reo への通知なし
  • P2 (warning): 日次 briefing (毎朝 07:00) にまとめて通知
  • P1 (critical): 即時 macOS push 通知 + Slack + Gmail

Layer 3 のビジネス指標が異常値になった場合は P1、Layer 2 のヘルスチェックが 3 連続失敗なら P1、Layer 1 のプロセスが 1 分以上停止なら P1、といった rule で自動判定します。

8.3 各マイルストーンで発生した実際の問題

M0 での問題: Ollama のモデル選定に 1 週間浪費しました。 llama3.2:3b が正解でしたが、mixtral-8x7b や llama3.1:70b を試してから戻ってきました。 教訓: 「小さいモデルで動くことを先に確認、必要に応じて大きくする」。

M1 での問題: 初 顧客 獲得までに 3 週間要しました。 プロダクト は 動いた が、cold email の 返信率 が 0.5% で、200 通 送って 1 顧客 という数字。 教訓: 「プロダクト 完成 と 顧客 獲得 は 別スキル」。

M2 での問題: handler queue の 8 ステージ で、learn ステージ の 設計 が 甘く、同じ handler が 何度 も 同じ error を 起こす パターン に。 教訓: 「learn ステージ は 単なる log ではなく、次回 route への feedback として 機能する 設計 が 必要」。

M4 での問題: Stripe webhook の 冪等性 保証 に 1 週間。 同じ webhook を 2 回 受信 して 二重課金 が 発生。 教訓: 「Stripe event_id を DB に UNIQUE 制約 で 保存、既存 なら skip」。
