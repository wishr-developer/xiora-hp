なぜ 2026-07-21 の タイミング で 復活 を 判断 した か

撤退 と 復活 の 間 に は 6 日 の 空白 が あり、その 間 に 復活 の 前提 が いくつ か 整い ました。 主 に 4 点 が 復活 判断 の 根拠 と なって います。

  • rafcid の 再 整備: 楽天 アフィリエイト ID (rafcid) が curation 用 途 (`wsc_i_ra_*`) と 出版/記事 用 途 (`wsc_i_is_*`) の 2 系統 に 整理 され、Vault (`xai:rakuten:rafcid_ra`) に 収容 されました
  • inventory DB の 事前 構築: 21 商品 の inventory (アフィリエイト URL / 本文 / 期待 値 EV2 / 対象 shop) が `services/systems/XioraLifeMedia/data/inventory.db` に 事前 に 整備 され、コンテンツ の 中核 が 属人 で ない 状態 に なりました
  • Xiora Rakuten Template Pack との 隣接: Insights 側 で 楽天 アフィリエイト を 前提 と した 記事 群 が 展開 され、curation と 記事 の 双方 で 楽天 経路 を 束ねる 目処 が 立ちました
  • Reo 明示 承認: Reo 代表 が 「復活」を 明示 で 承認 し、Playwright 経由 の semi-auto 投稿 も 認可 されて います

この 4 点 が 揃った 事 で、撤退 の 3 課題 (単一 依存 / 属人 / cross-sell 不在) を 構造 的 に 解決 する 余地 が 出て きた、と いう の が 復活 判断 の 前提 です。

変更 point 1 — 完全 自動化 (代理人 主導 の curation pipeline)

撤退 時 の 最大 の 課題 で ある「手動 属人」を、代理人 (AI エージェント) 主導 の 自動 化 で 置き換え ます。 curation の 各 段階 を 明確 に 分離 し、人 は 最終 承認 の み を 担当 する 分業 に 移行 する 想定 です。

  • 探索: 楽天市場 の 商品 メタ (価格 / カテゴリ / レビュー 数 / SEO キーワード) から 候補 を 自動 収集
  • 選定: 選定 基準 (価格 帯 / 期待 値 EV2 / 季節性 / shop 信頼 度) を 明文 化 し、しきい値 を 満たす 商品 のみ を 通過
  • 下書き: 商品 メタ を 元 に、Xiora 憲法 (誇大 / 断定 / 保証 なし) 準拠 の キャプション 下書き を AI が 生成
  • 投稿: Playwright 経由 の semi-auto 投稿 で、投稿 頻度 と 品質 の 両立
  • レビュー: 人 は 最終 承認 と スポット チェック だけ を 担当

Phase 1 の 段階 で は 一部 が 半 自動 (Playwright + 人 の 確認) で あって も、pipeline の 骨格 は 「代理人 主導」で 定着 させる 想定 です。 これ に より、投稿 頻度 が 運用 者 の 稼働 時間 に 直接 縛られない 状態 を 目指します。

変更 point 2 — 多 platform 統合 (4 channel 前提)

撤退 時 の 「単一 platform 依存」課題 を、多 platform 統合 の 前提 設計 で 解消 します。 Phase 3 以降 で 4 channel (楽天 ROOM / Amazon / もしも / 他) を 並列 で 走らせる 想定 で、コンテンツ 中核 は Xiora 側 の inventory に 蓄積 する こと で 移植 性 を 確保 します。

  • 楽天 ROOM: 復活 の 起点、rafcid `wsc_i_ra_*` を 使用、コレ / 投稿 の 2 経路
  • Amazon Associates: 楽天 に ない ブランド 商品 を 補完 (審査 通過 後)
  • もしも アフィリエイト: 楽天 / Amazon 双方 の 経路 を 束ねる 選択 肢 として 検討
  • 他 (バリコマ / A8 / アクセストレード 等): 商品 カテゴリ に 応じて 追加 (memory の XAI Asset Treasure Hunt 対象)

各 platform の 規約 は 個別 に 遵守 し (二重 投稿 / 誇大 表現 / prohibited 商材 の 除外 等)、コンテンツ の 全 同一 展開 で は なく、platform 別 の 適合 表現 で 展開 する 想定 です。

変更 point 3 — Xiora Rakuten Template Pack と の cross-sell

撤退 時 の 「cross-sell 経路 不在」を、Xiora 他 product との 相互 導線 で 解消 します。 特に Insights 記事 群 の 中 に 展開 されて いる 楽天 アフィリエイト リンク (Rakuten Template Pack) と、curation 投稿 を 相互 に 連結 する 想定 です。

  • Insights → curation: 記事 内 の アフィリエイト リンク の 隣 に「関連 curation」の 導線 を 貼る 想定
  • curation → Xiora HP: プロフィール 欄 / 投稿 補足 で Xiora HP / 12 product family へ の 導線 を 貼る
  • Xiora 他 SaaS との 相互 導線: KigenX (期限 管理) / Gourmie (生活 レビュー) 等 と 生活系 コンテンツ で テーマ 交差 する 部分 を 意図 的 に 相互 リンク
  • UTM 経由 の 経路 計測: 全 導線 に UTM を 付与 し、どこ から どこ に 流れた か を GA4 で 追跡

Phase 1 (W1) — ROOM 1 account 疎通

復活 の 起点 と なる Phase 1 は、楽天 ROOM の 1 account を 再 疎通 させる 段階 です。 inventory DB の 中 から 1 商品 を 目視 で verify し、投稿 経路 が 生きて いる こと を 確認 します。

  • 楽天 dashboard の 再 有効化 (Reo action)
  • Mac IPv6 fix (Playwright と 楽天 側 の 接続 安定化)
  • inventory 21 商品 の うち 1 item を 目視 verify (Reo action)
  • 投稿 pipeline の 最小 疎通 (探索 → 選定 → 下書き → 投稿 の 1 周)
  • rafcid `wsc_i_ra_*` の 経路 に アクセス が 流れる こと を 確認

Phase 2 (W2) — 3 account × 5 投稿 / 日

Phase 1 の 疎通 が 取れた 後、Phase 2 で は 投稿 頻度 と account 数 を 拡大 します。 3 account × 5 投稿 / 日 の 15 投稿 / 日 が Phase 2 の 想定 頻度 です。

  • account 2 / 3 を 追加 (規約 内 の 範囲 で、内容 を 分離)
  • 投稿 頻度 を 段階 的 に 引き上げ、品質 低下 の 兆候 を 監視
  • 期待 値 EV2 の 高い 商品 を 優先、下位 は 淘汰
  • Insights 記事 と の 相互 導線 を 開始

Phase 3 (W3+) — 4 platform 統合

Phase 3 で は 楽天 ROOM 単独 から、4 channel の 並列 運用 に 拡張 します。 Amazon Associates / もしも / その他 platform の 審査 通過 と、コンテンツ の platform 適合 が 中心 課題 です。

  • Amazon Associates 審査 通過 と 商品 導入
  • もしも 経由 の 楽天 / Amazon 二重 経路 化 (規約 内 で 選択)
  • 4 channel 横断 の inventory 共通 化 (`inventory.db` を SoT に)
  • Xiora 他 product との cross-sell 経路 の 標準 化
  • Phase 3 完了 時 点 で、XioraLifeMedia は Xiora 12 product family の 中 の 生活系 revenue engine として 定着

次章 予告 — Part 3 XioraLifeMedia system 設計

Part 3 で は、実装 側 の system 設計 (21 商品 inventory DB / 4 channel 統合 / Xiora HP family 12 中 の 位置 / 他 主力 SaaS との 補完 関係) と、参考 と した 実在 事例 (LTK / 楽天 ROOM 上位 curator) を 整理 します。 事業 化 済 の Xiora 主力 5 product に 続く 6 番目 の 位置付け として、他 product と どう 相互 補完 する か が 主 テーマ です。
